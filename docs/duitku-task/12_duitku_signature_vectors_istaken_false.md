# Task 12 — SHA256 parity vs Duitku PHP SDK reference vectors

**Status:** Not taken
**Owner:** API (takumipay-api)
**Spec reference:** `duitku_payout_provider_research.md` §2.4, §7 bullet 1

## Why this matters

Every Duitku request hinges on a SHA256 signature whose input is
order-sensitive unhashed string concatenation + the shared secret.
One field in the wrong position and the server rejects with `-191`
across the board. Duitku publishes a PHP SDK
(github.com/duitkupg/duitku-php) whose signature calls are the
canonical reference. Locking our builder's output to known-good
vectors from that SDK is the **only** way to have confidence the
byte layout is correct before we ever hit their sandbox.

**Depends on:** task 05 (`duitkuSha256` / `buildSignature`).

## Scope

Create `src/payout/duitku-signature.spec.ts`:

- One test per endpoint discriminant (five in total — `inquiry`,
  `transfer`, `inquiryStatus`, `checkBalance`/`listBank` share a
  formula so one test covers both, `clearingCallback`).
- Each test fixes a deterministic payload (email, timestamp, bank
  fields, etc.) and asserts `buildSignature` produces a specific hex
  string that matches the Duitku PHP SDK's output for the same input.

Getting the reference hashes:

- Clone `github.com/duitkupg/duitku-php` locally (outside this repo).
  Run the PHP SDK's signature functions in a throwaway script with
  the same inputs you hardcode in the test. Copy the hex output into
  the test fixture.
- Commit the fixture payloads + expected hashes. The PHP SDK is **not**
  a runtime dependency — we only consult it to generate the fixture.
- Leave a one-line comment above each fixture pointing at the PHP
  SDK commit hash the hash was derived from. If Duitku changes the
  formula, we re-anchor the fixture deliberately.

Additional tests:

- **Case sensitivity:** assert output is lowercase hex. Upper-case hex
  fails Duitku verification with `-191`.
- **UTF-8 safety:** include a fixture with a non-ASCII `purpose`
  field (e.g. an Indonesian character or emoji) to catch any
  accidental `binary`-mode hashing.
- **Secret not leaked in output:** trivially — signature output is
  hex, not the secret — but also assert the test log does not print
  `secretKey`.

Optionally: a round-trip test of `verifyCallbackSignature` (if task 05
stubbed it) against a PHP-SDK-generated callback payload — gate
behind a skip if the stub returns `false` for v1.

## Rules (non-negotiable)

- **Hand-type hash fixtures from the PHP SDK output.** Do not compute
  them with our own builder and paste them back — that would prove
  our builder is self-consistent, not that it matches Duitku.
- **Determinism.** No `Date.now()`, no random nonces in the fixtures.
  `timestamp` is a pinned integer.
- **Include at least one fixture with all optional fields present**
  (full `transfer` payload) and one with only mandatory fields.
- **The fixture commit message (or a comment in the spec) must
  reference the Duitku PHP SDK commit hash** used to generate the
  expected values. Without the anchor, a future mismatch has no
  reproducible baseline.
